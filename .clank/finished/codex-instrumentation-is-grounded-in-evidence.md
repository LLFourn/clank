# Codex instrumentation is grounded in evidence

## Why

Both agents on the main Clank team now use Codex. Background commands have been observed exiting in the UI without continuing the agent while its synchronous Stop hook is parked. The user suspects a recent Codex change. Establish whether that is a regression, a client/tool-path difference, or an unsupported assumption; do not choose an explanation in advance.

Clank removed its own completion wakes in `1252c3a9` (`a-run-ending-writes-nothing`) on the assumption that the harness reliably reports completion to the agent. A command-completed UI event and an actual model continuation are different observations. The research must establish the current supported way to instrument Codex as a whole, using this failure as a concrete acceptance case.

## Scope and deliverable

Produce a dated, source-linked `docs/codex-integration.md`, a small reproducible diagnostic fixture where needed, and concrete follow-up plan drafts. This is an investigation and integration recommendation, not a production transport migration or a restoration of `run_ended`. Deliver the complete research in one implementation commit after intro review.

## Investigation

1. **Inventory the actual runtime.** Identify the binaries, versions, clients, feature flags and execution paths used by the master and reviewer. Distinguish PATH's CLI from the daemon or app-bundled server actually serving a session. Record only relevant non-secret settings. Inspect Clank's existing Codex hooks, message routing, interrupt/release handling, attendance and transcript readers before proposing new machinery.
2. **Map current supported interfaces.** Use official documentation, release notes and source, plus schemas generated by the installed binary. Compare synchronous and asynchronous hooks; app-server notifications and subscriptions; thread/turn lifecycle and input APIs; background terminal inventory and output retrieval; session binding, questions/permissions and interruption. Distinguish native shell-tool runs, Code Mode wrappers, external process APIs and subagents. For each candidate interface record identifiers, ownership, compatibility/stability, ordering, reconnect/replay behavior, and whether it merely reports state or can actually continue the model. Do not infer a guarantee from an event name or from a UI update. Describe which observations still depend on unstable transcript formats.
3. **Reproduce the missing handoff.** In isolated temporary sessions, capture a timestamped trace of command start, process exit, client notification, hook start/end, turn status and model continuation. Use the same tool/client path as the reported failure first. Compare completion while a turn is active, while a synchronous Stop hook is parked, and after a turn has ended. Cover successful and failing commands, completion immediately around hook entry, and a no-Stop-hook control. Test native shell execution versus the wrapper path actually used here; treat subagent completion as a separate mechanism. Repeat the critical timing cases enough to expose unreliability, with bounded observation windows and explicit cleanup.
4. **Test the recent-change hypothesis.** Compare the current serving version with a known previously working version if one can be established, and relevant recent official changes. Run a minimal comparison under equivalent configuration when practical. Existing preliminary inspection found similar shell-exit event emission in CLI 0.160.0 and 0.167.1; that alone neither proves nor disproves a behavioral regression elsewhere. If the old behavior cannot be reproduced, label the regression attribution unproven and record the missing evidence.
5. **Recommend a Clank contract.** State the supported primary interface and any narrowly justified fallback for binding, observing work, delivering input and resuming a parked agent. Evaluate the existing monitor-owned process lifecycle evidence as well as native event subscriptions. Address lost connections, restart, duplicate completion, completion-before-subscription, stale sessions, and independent master/reviewer sessions. Process disappearance is not proof of success or an exit code. Keep hooks minimal: transport session facts and monitor decisions; do not read monitor-owned configuration or duplicate its policy. Preserve event-driven operation and avoid returning to message-log/timeline spam just to obtain a wake.
6. **Turn findings into actionable follow-ups.** Draft narrowly scoped implementation plans with acceptance criteria and migration implications. Include correction of skills/docs that promise an unconditional harness wake if the evidence does not support it. Provide an upstream-ready minimal reproduction if the failure belongs in Codex. Clearly separate documented guarantees, observed behavior, source inference and unresolved questions.

## Diagnostic constraints

- Do not experiment on the team's live sessions, global hook/config files, or the website-art worktree. Use isolated configuration and temporary directories, bounded commands, and explicit teardown; no destructive probes or sensitive trace output.
- Prefer a small Rust diagnostic fixture and shared tooling. No Python dependency, no shell/process scaffolding where an in-process seam suffices. Real Codex/process execution is justified for the actual cross-process handoff experiment; keep it out of default CI if it requires credentials or a model session.
- Do not rely on the disputed completion wake to finish the investigation. Use bounded synchronous probes or an explicitly arranged independent check-in, and register any background work with Clank.
- No global upgrade/downgrade, tag change, production integration change, or new polling loop as part of this research.

## Done when

The report identifies the actual tested versions and execution paths, provides replayable evidence for the parked-hook completion case (or an explicit bounded inconclusive result), and recommends a current Codex integration contract for both agents. Every claimed wake guarantee is backed by documentation or a reproducible observation with its limits stated. A reviewer can run the diagnostic, understand cleanup and expected traces, and assess the proposed follow-up plans without relying on this conversation.

## As implemented

`docs/codex-integration.md` records the runtime inventory, official documentation,
installed schemas, source/history inspection, interface contracts, existing Clank
integration and bounded experimental results. The installed default is 0.167.2;
both inspected live team processes still serve 0.167.1. A recent regression is
unproven: there is no known-good historical terminal reproduction.

An ignored Rust diagnostic extends the shared isolated question-protocol fixture
and existing process helper. It drives real native shell and Code Mode shell
calls through app-server with a scripted local model, temporary profiles and
socket barriers. The final matrix passed 32 cases on each of 0.167.1 and 0.167.2:
all native exits had the expected code; none caused another model request in
the two-second observation window. All 48 explicit hook-continuation controls
worked. The fixture does not exercise the actual TUI, a yielded Code Mode cell,
subagents or external model inference; these remain explicit evidence gaps.

`docs/codex-followups.md` contains three reviewable implementation drafts, also
staged in `.clank/drafts`: monitor-owned completion custody without timeline
spam, verified native endpoint ownership, and hook/version readiness diagnostics.
They are not queued or implemented by this research commit. Hooks and production
policy remain unchanged.

Validation: the installed-provider matrices above, the existing native-question
replay/arbitration test on 0.167.2, and CLI integration-test Clippy with warnings
denied passed. Tests require no Python, credentials or paid inference. The
experiment used an independent timer because its disputed completion path could
not be trusted to wake the investigator.
