# Codex integration evidence

Investigation date: 2026-11-13 (Australia/Sydney). Baseline: Clank v0.2.0,
`5410fb629548341594a9de0bab7316bfc20ce2b2`. This report distinguishes direct
observations, source inference, documented behavior, and proposed changes.

**Follow-up:** [Actual-TUI background-work evidence](codex-tui-background.md)
closes the client-ownership and unregistered-command questions left by this
first investigation. It captures live Stop/tool/subagent hooks, tests a private
per-agent server with the real TUI, and exercises Clank's disposable fork path.
Its recommendation and coverage limits supersede this report's open endpoint
questions; it does not establish a known-good regression baseline.

## Question

A background command displayed “Exited” without continuing an agent parked in
Clank's synchronous Stop hook. Is this a recent Codex regression, and which
interfaces should Clank use now?

**Finding:** the controlled native-shell and Code Mode-wrapper probes on
0.167.1 and 0.167.2 receive a command-completed event without another model
request during the observation window. This also occurs with no Stop hook
after a normal turn end. A Stop hook explicitly returning a continuation does
resume the model. These observations establish a gap in Clank's assumed
handoff for the tested engine paths; they do not establish a recent TUI
regression or show that every kind of background work behaves alike.

Clank's `1252c3a9` removed completion wakes on the assumption that the harness
would continue the agent. The finished `a-run-ending-writes-nothing` plan
explicitly tested that process retirement produces no wake; it did not test
the native Codex handoff. The report from the user establishes an operational
failure, but does not by itself identify the responsible layer or version.

## Interfaces and guarantees

The official [app-server documentation](https://learn.chatgpt.com/docs/app-server)
describes a bidirectional JSON-RPC interface. Start/resume subscribes a client;
read alone does not. Turn inputs, cancellation, item notifications and external
process control are separate operations. Native approval/question requests use
request IDs; resolution can mean cleanup rather than a successful answer.
Experimental methods require an explicit capability opt-in.

The following inventory was also checked against JSON schemas generated by the
installed 0.167.2 binary, rather than assumed from the latest documentation:

```sh
codex app-server generate-json-schema --experimental --out /tmp/codex-schema
```

| Surface | Identifiers / evidence | Appropriate Clank use and limits |
| --- | --- | --- |
| `initialize` / `initialized` | connection, client metadata, negotiated capabilities | Establish compatibility before using methods. Generate schemas from each supported version; presence of a field alone is not a behavioral guarantee. |
| `thread/loaded/list`, `thread/read` | thread ID, cwd, runtime status | Verify the intended thread is already hosted by the intended endpoint. Never load an old rollout into a different server merely to make routing succeed. |
| `thread/resume` | thread ID and returned live state | Subscribe only after validating ownership. Do not treat reconnect as replay of every missed notification. Reconcile history and pending requests. |
| `turn/started`, `turn/completed`, `thread/status/changed` | thread ID, turn ID, terminal status | Observe turn lifecycle. An interrupted or failed turn is not successful completion. |
| `item/started`, `item/completed` | thread ID, turn ID, item ID; command execution status, output, exit code | Observe native tool lifecycle. A client update is not itself a request to continue the model. |
| `hook/started`, `hook/completed` | thread ID, optional turn ID, hook run ID, event name, execution mode, timestamps, status | Distinguish a synchronous parked Stop hook from active model work. Reconcile after reconnect; do not assume an unobserved hook start never happened. |
| `thread/turns/list`, `thread/items/list` | pagination cursors, turn/item identity | Snapshot reconciliation and historical display. Use current pagination rather than requiring full rollouts. Availability and history mode must be checked. |
| `thread/backgroundTerminals/list` | process ID, item ID, command, cwd, optional OS PID | Experimental running inventory. A missing process is not an exit code or a completion replay. Do not continuously poll it. |
| `turn/steer` | expected active turn ID | Submit input to working turns with a concurrency guard. Acceptance does not prove a parked hook was interrupted or the model consumed the input. |
| `turn/interrupt` then terminal turn event | thread and turn IDs | Cancellation acknowledgement is not the terminal event. Do not start replacement input until the cancelled turn is actually released. |
| `turn/start` | thread ID; optional `turnTrigger`; user input or standalone `toolOutput` | Explicit continuation for an idle thread. `toolOutput` is for output owned by the client, not fabricated completion of an unrelated native tool call. |
| `item/tool/requestUserInput`, approval requests, `serverRequest/resolved` | native request ID plus thread/turn/item IDs | Preserve request identity and native arbitration. Never interpret resolution alone as evidence of which answer won. |
| `command/exec` | command execution request/session | Runs outside a model thread/turn. Useful for client-owned commands, not evidence about native shell-tool auto-continuation. |
| `process/*` | client process handle, exit/output notifications | Experimental unsandboxed process control. Not a substitute for the sandboxed model tool path or an appropriate workaround here. |

The table is a proposed adapter responsibility map, not a claim that every
method is currently reachable from Clank's `--no-daemon` TUI launches. Endpoint
ownership and availability must be solved before a monitor subscribes.

The official [hook contract](https://learn.chatgpt.com/docs/hooks) says that a
synchronous Stop hook can continue the model by returning a blocking decision
with a reason. An asynchronous hook's completion does not start an idle turn;
its informational output waits for a suitable model boundary. Therefore making
Clank's Stop hook asynchronous is not an established solution. The docs also
warn that transcript formats are unstable. Hook payloads and lifecycle events
are preferable to parsing presentation text.

Hook discovery is not readiness: the first isolated probes discovered an
enabled Stop hook whose `trustStatus` was `untrusted`; the turn completed
without running it. Current Codex requires trust in the exact definition.
The fixture now validates that its inventory contains only its generated
temporary hook, then uses the same `config/batchWrite` trust-hash update as
[Codex's hook UI](https://github.com/openai/codex/blob/rust-v0.167.2/codex-rs/tui/src/hooks_rpc.rs).
This touches only the temporary profile. Production diagnostics should guide
native hook review, not bypass trust or automatically trust arbitrary hooks.

Keep API `thread.id` separate from `thread.sessionId`: the latter can identify
a shared root across forks. Binding a Clank agent must identify its concrete
thread and owning server, not merely that shared root.

## Source tracing

Source inspection is evidence about a code path, not a promise about every
client, model extension or hosting environment:

- In [0.167.2's unified-exec exit watcher](https://github.com/openai/codex/blob/rust-v0.167.2/codex-rs/core/src/unified_exec/async_watcher.rs),
  process exit and output draining lead to an execution-end emission. That
  function does not start a turn. Earlier inspection found the same basic
  structure in 0.167.1 and 0.160.0; this is not a complete behavioral bisect.
- The emission goes through `ToolEmitter` and the session's item-completed
  event path. The session also has extension callbacks, so the watcher alone
  cannot establish what every hosting client subsequently does.
- [The Stop-hook runtime](https://github.com/openai/codex/blob/rust-v0.167.2/codex-rs/core/src/hook_runtime.rs)
  emits hook-start events, awaits the hook engine, then emits completed events.
  The turn loop awaits that result before acting on its continuation decision.
- [Code Mode's delegate](https://github.com/openai/codex/blob/rust-v0.167.2/codex-rs/core/src/tools/code_mode/delegate.rs)
  routes explicit `notify` calls through `inject_if_running`, with an error if
  no active turn exists. This is a different path from the shell exit watcher;
  neither an explicit notification nor a completed cell should be conflated
  with a nested shell process that outlives the cell.
  [The injection implementation](https://github.com/openai/codex/blob/rust-v0.167.2/codex-rs/core/src/session/inject.rs)
  queues input on a non-finishing active turn. Queue acceptance alone does not
  demonstrate interruption of an awaited Stop hook.
- The [0.167.2 changelog](https://learn.chatgpt.com/docs/changelog) lists incremental
  tool updates for Google Cloud Vertex AI. It does not document a fix for this
  Stop-hook symptom. Absence from the notes is not proof that no fix exists.

The history search also found concrete changes to adjacent behavior:
[preserving early shell output in completion events](https://github.com/openai/codex/commit/d47b9a8c002f41433784fef2536892d49c9facfb)
and [updating completion/poll buffers atomically](https://github.com/openai/codex/commit/4891c4e35fe8b306433f6c0f04dd74bd9e4257e9)
in September, and a [hook-trust override propagation fix](https://github.com/openai/codex/commit/d007b0852ad75ce8f365c14f2b8d8dd91ed0eae6)
in June. These are relevant compatibility lessons, not evidence that automatic
shell-completion continuation was recently removed. No culprit commit was
established, and no known-good-to-bad bisect is claimed.

## Existing Clank integration

`cli/codex_chat.rs` already distinguishes working turns, idle threads, and a
turn with a final answer still in progress. Its last case interrupts, waits
for release, then starts the message. It refuses to load the target into an
unrelated control server. However, it guesses a common socket location, and
final-answer presence is an inference about hook state. A persistent native
observer should replace those assumptions with verified endpoint identity and
hook lifecycle evidence where supported.

`cli/codex_interrupt.rs` and the native question protocol test provide existing
building blocks. Reuse these rather than adding another unrelated RPC client.
The question fixture already tests reconnect/replay and competing answers;
that does not establish command-completion replay.

`cli/monitor.rs::retire_gone_runs` already receives process-lifecycle evidence,
retires attendance, and re-serves the parked wait for other owed work. It does
not manufacture a completion item. `clank run` execs the child and does not own
its output or retain an exit status. A new fallback must not report success
merely because the registered PID/birth is gone.

Transcript coupling remains in `cli/web/transcript.rs`, `cli/wake_repeat.rs`
and the session probe. Chat rendering can degrade to a historical snapshot;
delivery custody and live permission state need stronger evidence. A migration
should be incremental, preserve old logs, and explicitly report unsupported
native capabilities rather than silently treating missing data as idle.

## Recommendation

Separate observation from delivery. Prefer one monitor-owned adapter per
verified Codex endpoint, consuming native events and projecting typed facts
into Clank's existing turn policy. Key observations by server generation,
concrete thread, turn, item/process and hook run. A reconnect invalidates any
claim of uninterrupted observation: subscribe, reconcile a snapshot, dedupe
the overlap, and leave unresolved state unknown.

Keep the hook a messenger, as required by [hook-boundary.md](hook-boundary.md).
The monitor decides whether completion needs attention; the synchronous hook
can carry that decision while parked. For a released/idle thread, a native
turn-start transport needs an explicit ownership and delivery contract. Do not
interrupt genuine model work simply because another process ended. Do not
change global Codex configuration or resume every stored session to obtain a
control endpoint.

If native completion cannot guarantee attention, retain a separate pending
completion obligation in monitor custody, not a message-log entry or timeline
row. Its receipt must survive a lost hook reply and monitor restart, avoid a
second continuation when native delivery already succeeded, and never cross
an agent rebind. Design that obligation only after the diagnostic results are
known. Correct unconditional wake promises in shared skills alongside the
delivery implementation.

## Diagnostic and remaining evidence

The opt-in Rust diagnostic reuses the isolated Codex question-protocol server
and a scripted localhost model. No external inference, credentials or global
configuration is used. It drives a real unified-exec command and a real Stop
hook with socket barriers, observes native events, and counts model requests.
Ordinary CI does not run installed-provider experiments.

### Reproduce

Use an absolute path to a locally installed binary with its matching
`codex-code-mode-host` sibling. This does not install or upgrade Codex:

```sh
CLANK_CODEX_PROTOCOL_BINARY=/absolute/path/to/codex \
CLANK_CODEX_PROBE_TRACE_DIR=/tmp/codex-completion-evidence \
cargo test -p clank --test it \
  codex_question_protocol::completion:: -- --ignored --nocapture
```

Allow localhost listeners and child processes. The test clears the child
environment, creates fresh HOME/CODEX_HOME/cwd, and uses a local scripted
Responses server with a fixture-only key. The real Codex process executes only
the shared Rust test binary. Its test thread permits that owned command; no
production permission setting is changed. No Python, credentials or paid
model call is involved. The default suite skips the experiment.

Each scenario uses a fresh server/profile. The first model request calls
`exec_command` directly, or calls Code Mode `exec` with
`text(await tools.exec_command(...))`. The command waits at a socket barrier
and yields a running-session result. A second model request is held by the
driver, then returns a final answer. Exit is released while that request is
active, on observing the final-answer event at the hook-entry boundary, while
Stop is parked, or after the no-hook turn has ended. Both exit 0 and exit 7
are tested twice in each mode. The boundary scenario accepts either ordering
of command completion and hook start and retains an already-observed exit.

The driver distinguishes textual native results from Code Mode's structured
`session_id` result. It verifies a real yielded command, checks the native
exit-code event, then observes for two seconds without sending model input.
For parked cases, it subsequently sends `decision: block` through the hook
as a positive control, verifies a third model request, and releases the next
hook normally. That third request must not be attributed to process exit.

Trace files include monotonic milliseconds, thread/turn identity, native
notifications, the yielded result, barrier releases and the model-request
count at the observation deadline. They contain only the synthetic session.
The runner bounds RPC/event waits to ten seconds and fixture socket waits to
twenty seconds. The owned server group is killed/reaped on scope exit, the
local model tasks are aborted and temporary profiles are deleted. Fixture
processes also have their own deadline if the driver disappears. Trace output
is retained at the explicitly requested directory; remove that directory
after collecting evidence. A run that fails before the exit event is a setup
failure or inconclusive probe, not evidence for a missing wake.

### Limits

This controls the engine and real Code Mode host through app-server. It does
not drive the actual terminal UI, a ChatGPT app integration, a real model's
choice of tools, a long-lived yielded Code Mode cell, or subagent completion.
The boundary case releases the command on receiving the final-answer event;
it cannot force a particular scheduler ordering inside Codex. A two-second window
establishes absence of prompt continuation in that window, not a theorem that
no later timer, extension or client could continue the turn.

No known-good historical reproduction or timestamped trace from the user's
original failing terminal was available. The claim of a recent regression
therefore remains unproven even if the tested versions behave identically.
An upstream report should provide the fixture and trace, specify these limits,
and ask whether automatic continuation is intended for this execution path;
it should not assert a removed guarantee or a particular culprit commit.

Clank tells a Codex agent when a `clank run` ends and observes no native
background work; see [codex-tui-background.md](codex-tui-background.md).

### Measured results

The final comparison completed on 2026-11-13 using the standalone macOS ARM64
binaries for each version. Each version ran 32 cases: two tool paths × four
exit phases × two exit codes × two repetitions.

| Observation | 0.167.1 | 0.167.2 |
| --- | --- | --- |
| Native command completion with the requested exit code | 32/32 | 32/32 |
| Another model request within the two-second observation window | 0/32 | 0/32 |
| Explicit Stop-hook continuation positive control | 24/24 | 24/24 |
| Cases completing the diagnostic successfully | 32/32 | 32/32 |

The eight no-hook idle cases per version have no hook positive control. Every
case observed exactly two model requests before the control: the request that
issued the tool call and the request that produced the final answer. The
diagnostic records this count rather than asserting that missing continuation
is correct behavior. Passing means the experiment completed and its explicit
controls worked, not that Clank's current delivery contract is sound.

One representative 0.167.2 native parked-success trace, in milliseconds from
scenario start:

| Time | Observation |
| --- | --- |
| 320 | Command reaches its socket barrier |
| 708 | Second model request; yielded tool result names a running session |
| 728 | Stop hook reaches its barrier; driver releases command |
| 730 | Native command-completed event reports exit 0 |
| 2732 | Observation ends with two model requests; driver releases hook with `block` |
| 2756 | Second Stop-hook invocation after the verified third model request |

Full synthetic traces from this run were retained locally under
`/tmp/clank-codex-final-01671` and `/tmp/clank-codex-final-01672` (32 JSON files
each). Those temporary artifacts are not required to reproduce the experiment;
the fixture and this result summary are committed. The validation log was
`/tmp/clank-codex-research-validation.log`, with exit status 0.

Validation also passed `cargo clippy -p clank --test it -- -D warnings` and the
existing ignored native-question replay/arbitration test on 0.167.2. The
completion matrix ran against both versions; the full workspace suite was not
run for this research-only change. No live team session was restarted.
