Chapter 5: the third pattern

A controller repo

Some repos exist to run other repos. Their agents are woken by the outside world, such as a pull request, a timer or a feed you wrote, and they react by handing work to the teams they supervise.

Wake sources

An agent’s wake sources live in its own config, .clank/agents/label/config.json, as a wait_events list. The repo’s monitor hosts them for as long as it runs, and every event they produce lands in that agent’s inbox before it wakes anyone. There are three kinds.

Timers

{
  "wait_events": [
    {"kind": "timer", "name": "morning-sweep",
     "due_at": "2026-11-02T09:00:00+11:00",
     "repeat_every": "24h",
     "content": "Route each open PR to its team."}
  ]
}

A timer fires once at due_at, an absolute time with an explicit UTC offset. With repeat_every it fires again at that fixed interval. That is elapsed time, not a calendar: 24 hours stays 24 hours across a daylight-saving change. If clank was not running when a timer came due, it catches up the next time a wait is armed. A recurring timer that missed many slots delivers one catch-up event for all of them, not a storm. Acknowledging that event covers every slot up to the moment you acknowledged it.

Command sources

{"kind": "command", "name": "deploys",
 "command": ["deploy-feed", "--follow"]}

A command source is any program that writes one JSON object per line on stdout. Each line needs an id that is unique within the source, and may carry content, kind and at. clank deduplicates on the id, so a producer may repeat itself safely. The argv runs without a shell, in a process group clank owns and ends when its host stops. Add reply_command and a line can set "requires_reply": true, so the agent must answer the event before it can acknowledge it.

This is the general escape hatch. An HTTP long-poll, a chat receiver or a script that watches a log can each become an event source in a few lines.

GitHub

{"kind": "github", "repo": "owner/name",
 "watch": [
   {"pr": {"events": ["opened"]}},
   {"pr": {"numbers": [603], "events": ["review_submitted", "comment"]}},
   {"branch": {"names": ["main"], "events": ["push"]}}
 ],
 "prompt": "Triage it, hand it to the right team, then ack."}

A GitHub source watches a repo’s pull requests, issues, branch pushes and CI conclusions. The watch form names objects and the events under each one. Clauses add together, and an event that several clauses admit still wakes you once. There is also a flat form, "events": ["pr_opened", "pr_comment"] with optional "prs" and "branches" scopes. A source uses one form or the other, never both.

  • prompt is your standing instruction for that watch. It is shown with every event the watch produces, telling the agent what reacting means.
  • Your own actions don’t wake you, unless you set "include_own_actions": true. The exception is review_submitted, which is never filtered, because a submitted review is the thing a team waits on.
  • CI conclusions are read, not received. ci_passed and ci_failed come from asking each watched PR’s head what its checks say. A wait sees the current result. A red build that turned green while nothing was armed is simply gone.

A source polls by default. Add "delivery": "realtime" for push-speed wakes through GitHub’s webhook forwarding. Polling keeps running underneath as the backstop. What each needs:

DeliveryNeeds
PollingA token from GH_TOKEN or GITHUB_TOKEN, or else one gh auth token call. With neither, the source waits and says so. It never polls unauthenticated.
RealtimeThe gh binary, its cli/gh-webhook extension, and admin on the watched repo, because it creates a webhook. Without them the source falls back to polling and names the reason once.

The clank-github skill carries the full vocabulary, catch-up rules and realtime caveats. Agents load it when GitHub events wake them.

The inbox: react, then ack

Every event a source delivers, and every message clank send delivers, goes into the recipient’s inbox, a log under its agent directory in .clank/agents/. It stays unhandled, and keeps waking its agent each time a wait is armed, until the agent acknowledges it. Delivery is therefore at least once. An event that fires while the agent is offline is waiting when it comes back, and one it half-handled before a crash comes round again.

clank events list
clank events read id
clank events ack id

list and show give metadata only. read returns the content and records that it was delivered to you. Event content comes from outside, so treat it as untrusted. The loop is always the same: read it, do what it asks, acknowledge it. Reading or being woken never acknowledges anything. An event that requires a reply is acknowledged with its answer: clank events ack id --reply "Shipped in 1.4.2."

Watching another repo

clank wait --repo ../app --for finished

This is an observer wait. It blocks until the named thing happens in that repo, counting only what happens after it starts: commit for any new commit, finished for a finalized plan, stopped for a plan finalized or a new unanswered block. It needs no binding in the other repo and fires no lifecycle hooks.

An observer wait is not your work loop.

Your own work still reaches you the way it always does: through your tool’s hook or plugin, or for Grok through its one requested background wait. An observer wait is a deliberate, separate command you start to watch someone else’s repo, and its completion is your signal. It does not replace, and must not duplicate, your automatic subscription. For agents states the whole contract.

Talking across repos

clank send --repo ../app --master -m "PR 612 needs a review pass before Friday."
clank send --repo ../app --to codex --reply-to lead -m "Is main green after the merge?"

A message is a durable event in the recipient’s inbox, and it wakes them until they acknowledge it. --master addresses whoever that repo’s roster names master. --reply-to names one of your own agents and requires an answer before the recipient can acknowledge. --interrupt also tries to interrupt the recipient’s current turn. If that cannot be done, the message waits in the inbox as usual.

Spawning and supervising teams

Nearly every command takes --repo, so a controller agent can set up and drive a team elsewhere with the same commands you would use:

clank init --repo ../app --team review-pair
clank open --repo ../app
clank queue add fix-flaky-ci --repo ../app -m "Make the integration job deterministic."
clank wait --repo ../app --for stopped
clank status --repo ../app

That team’s master is handed the queued plan and runs the cycle on its own. The controller watches for the stop-point and reads the result. When the other team blocks on a question, the controller sees the stop and can relay the question to you.
