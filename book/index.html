clank

Coding agents from different vendors review each other’s work, one plan at a time, and the plan lands in your git history as a sealed record. clank decides whose turn it is and wakes that agent, so nobody has to chase anyone.

This book teaches clank to the people who run a team of agents and to the agents on that team. It starts with why clank works the way it does, then walks through the three ways people use it, with recordings of real runs.

What clank is

clank is a command-line tool that runs a team of coding agents in one git repository. The agents are the CLIs you already use: Claude Code, Codex, Grok and opencode. One agent is the master. It writes plans and implements them. The others are reviewers, and they read the master’s commits and write a verdict on each one. clank keeps the state of all of that in the repo, works out who owes the next move, and wakes that agent with the work.

You open the whole team in a zellij session with one command and watch it from a terminal dashboard. You step in when an agent asks a question only you can answer.

Five ideas the rest of the book depends on

  • One plan at a time, reviewed by another mind

    A repo has at most one active plan, a markdown file under .clank/plans/. Starting it is a commit, [plan] intro, so the plan is reviewed before any code is. The master then implements the whole plan in one commit, and the reviewers on the roster read it. They work best when they come from a different vendor than the master, because a model is a poor judge of its own blind spots.

  • The plan’s history is the git history

    Everything a plan becomes is a commit: its introduction, each revision, the implementation tagged [plan], and the finish commit that moves the plan into .clank/finished/. The finish message describes the whole plan as if it were one commit, because with finish.autosquash on, it becomes one. More than five hundred finished plans in clank’s own repo are the record of how it was built.

    The verdicts are files too, kept per reviewer and keyed by commit. They stay local to your checkout: they drive the cycle while it runs, and the sealed plan is what is left once it is done.

  • Agents are woken; you are never the scheduler

    When an agent ends its turn, clank decides whether it has work. If it does, the agent gets it at once. If it does not, clank holds the agent until there is some. No agent polls, and you never type “your turn” into a pane. When an agent needs a decision only a human can make, it raises a block, and your answer wakes it.

  • Roles come from the roster, not from flags

    The repo’s roster lists each agent, its tool and its role: master, a reviewer tier, or standby. A session is bound to its roster label when it starts, and its role is read from the roster every time it is needed. To change who is master you edit the roster, with clank agent make-master, and nobody has to relaunch with a different flag.

  • Manual control where it matters

    clank automates whose turn it is. It does not automate the decisions that are hard to undo. The master finalizes a plan only when the review gate says FINISHED, and it has to write the summary itself. History rewrites like autosquash are a setting you turn on. When an agent's turn ends on a provider error, or it stops with work still pending, clank retries a bounded number of times and then hands it to you; past that point a wedged agent is yours to nudge. Auto-mode is per agent, and clank auto off hands a session back to you.

What clank is not

The README’s tagline is out of date. It still says “no daemon”. There is a per-repo monitor now; this section says what it is.

It is not an agent. It has no model of its own. It launches the agent CLIs you have installed, teaches them their role through skills and hooks that clank setup installs, and routes work to them.

It is not a hosted service. Plans, the roster, verdicts and the event inbox are files in your repo’s .clank/ directory and in ~/.clank/. There is no database and no account.

It does run one background process per repo: the monitor. The first clank wait or clank tui in a repo starts it. It watches the repo once on behalf of every agent and dashboard, hosts the event sources agents have configured, and decides what each agent’s turn-end means. You never install, start or configure it, and none of your durable state lives inside it. How it works has the details.

The remote is optional. clank can serve the team to a browser or phone, but only when you switch it on. That is the one part of clank that runs a web server, and its chapter covers what that costs.
