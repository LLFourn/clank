Chapter 4: the second pattern

Teams and forks

Once a team works, you want it again in the next repo, and on several pieces of work at once. Teams are saved rosters. Forks are the whole team carried into a new worktree, conversations included.

Your library: agents and teams

Your user-level config, ~/.clank/config.json, holds two libraries that every repo can copy from.

An agent description is a tool and how to launch it, with no role. Save one, then add it to any repo’s roster by name:

clank team agent add opus --tool claude -- --model opus
clank agent add opus --review final

Everything after -- is passed to the tool exactly as you would type it. Keep it to the few flags that pick a configuration. MCP servers and feature switches belong in the tool’s own config, or in a per-agent home set with --env. clank agent launch opus shows the launch an agent has and the command clank agent start would run.

A team is a saved roster. Save the one this repo has, and seed another repo from it:

clank team save review-pair
clank init --team review-pair

A team saved as default seeds every bare clank init in a repo with no roster. clank team list and clank team show review-pair show what you have. clank agent swap bob kimi replaces one reviewer with another in a single write, so the role is never empty.

Forking the team

clank fork create retry-work

This creates a linked git worktree at .clank/worktrees/retry-work on a new branch of the same name, and gives it the team. Inside zellij it opens the fork as a new tab at once. Use --no-open to skip that.

The agents in the fork don’t start blank. Each one’s session is forked from the one it has in the source repo: Claude through its own session fork, Codex through codex fork, and Grok by preparing its history in the new worktree before launch. So the forked team remembers the conversation that led to the fork. An agent with no session to fork starts fresh, but carries an orientation prompt telling it where it is. --fresh starts every agent that way on purpose.

Shaping a fork

  • clank fork create retry-work --draft retry-plan moves a draft into the fork’s queue, so the forked master is handed it first. Repeat --draft to queue several in order.
  • clank fork create docs-pass --team review-pair seeds the fork’s roster from a saved team instead of copying this one.
  • clank fork create --pr 42 fetches the pull request’s head, bases the worktree on it, and orients the forked sessions to reviewing PR #42 by its title. It uses gh.
  • clank fork create scratch --clone makes a full local clone under .clank/clones/ instead of a worktree. It is an independent repo whose only remote is your checkout.
  • clank fork create retry-work --prompt "Focus on the retry path only." adds your own context to the orientation.

Working several forks at once

A fork is a repo in its own right. It has its own roster copy, its own master and its own single active plan. Several forks therefore run in parallel without stepping on each other, each in its own tab.

clank fork list
clank open --fork retry-work
clank open --all

clank open --fork retry-work reopens that fork’s tab, and does nothing if it is already open. --all opens every fork that isn’t open yet. Each fork starts its whole team, so do that on purpose.

Landing the work and cleaning up

A fork’s plans finish on the fork’s branch. To bring finished plans onto your branch, copy them, commits and plan files together:

clank pick --from retry-work add-retry

pick never changes the source branch. --squash lands each plan as one commit, and --dry-run shows what would land first. An ordinary git merge works too. When you are done:

clank fork remove retry-work

Removal refuses a fork with uncommitted changes or commits your checkout cannot reach. --force overrides that, and for a clone it permanently destroys those commits.
