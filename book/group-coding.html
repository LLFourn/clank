Chapter 3: the first pattern

Group coding

The everyday pattern: one master and its reviewers take a plan from a draft to a sealed record, with every commit reviewed on the way.

Who does what

The master writes plans, promotes them, implements them and finishes them. It never writes verdicts. The reviewers read the master’s commits and write exactly one verdict on each commit they owe. They never promote, implement or finish. A standby agent reviews nothing. It is still woken for everything else, such as messages and events, which makes it a good place to keep a helper.

Drafts, the queue and promotion

A plan starts as a markdown file in .clank/drafts/, a staging area git ignores. Queuing it consumes the draft. Promoting it makes it the repo’s active plan:

# write the plan body first, in .clank/drafts/my-feature.md
clank queue add my-feature
clank queue promote my-feature

The queue is ordered by priority, lowest first and 500 by default, so clank queue add my-feature --priority 200 jumps it ahead. clank queue unqueue my-feature sends a queued plan back to drafts, and clank queue remove my-feature deletes it.

Promotion is a commit: the plan file lands in .clank/plans/ as [my-feature] intro. That commit is the plan’s first review. Reviewers read the plan before any code exists, which is the cheapest moment to say the plan is wrong.

When no plan is active and the queue is not empty, clank hands the master a promote item. The master reads the queued plan against the code as it is now, rescopes or splits it if it needs that, and promotes only what is ready.

In clank tui the queue has a drafts row under it. A draft’s page can queue it with e, or queue and promote it with p.

Reviewer tiers

Each reviewer on the roster has a tier, which says which commits it owes a verdict on.

TierReviews
commitEvery reviewable commit, as it lands.
planThe plan stage: the intro and any plan revisions.
finalThe final stage, when the work is believed complete.
gateBoth the plan stage and the final stage.
standbyNothing. It is woken for everything else.

Change a tier in place with clank agent set-review bob gate. The agent’s session and pane are untouched.

Verdicts, and what each one obliges

A reviewer writes its verdict with one command:

clank feedback write --commit sha --verdict request-changes \
  --author bob -m "The backoff never stops growing"

The first line of -m is the summary and any further lines are detail. clank prepends the verdict itself. Together, the verdicts on the latest reviewable commit make up the plan’s review gate.

CONTINUE
The commit is sound and nothing in it is being held up, but the plan still owes work. The reviewer names what remains. A reviewer that is waiting on a change it asked for must not write CONTINUE.
REQUEST_CHANGES
A correction is required before anything else happens. The master makes it, commits, and stops for review again. It is also the right verdict for an implementation delivered in pieces without milestones the plan justified.
FINISHED
The committable work the plan describes is done and ready to merge: code written, tests passing, review satisfied. A plan document alone is not finished unless the document is the whole deliverable. A step only a human can do, like a smoke test on a device, is recommended in the verdict, never waited on.

A single REQUEST_CHANGES holds the plan, whatever the others said. The gate reaches finished when a reviewer writes FINISHED and nobody has asked for changes. While a gate-tier reviewer still owes its verdict, the master waits. The master reads the verdicts with a command, not by opening the files:

clank feedback read --commit sha
clank feedback read --plan

The second form reads the active plan’s whole cycle, oldest commit first, each with its verdicts.

One commit, or justified milestones

The master implements everything a plan specifies in a single commit. A plan can name internal milestones, but only with a strong reason for each review boundary, written into the plan before implementation starts. Milestones added afterwards to excuse a partial commit are what reviewers are told to reject.

After every commit the master stops: after the implementation, after each review correction, after a plan revision, and after promoting a plan. clank wakes it again when the gate has moved. The For agents chapter has the rule from the agent’s side.

Commit tags

An implementation commit’s subject starts with the plan it belongs to, as in [my-feature] Retry failed fetches. The tags on a commit must equal the set of active plans whose files it touches: no tag on an unrelated fix, and no missing or extra tag. If they don’t match, clank hands the master a correction to amend before anything else moves.

Finishing a plan

When the gate reaches FINISHED, the master is handed a finalize item, and only then does it run:

clank finish my-feature -m "Retry failed fetches with a capped backoff" \
  -m "CI flaked on every network blip, and an uncapped retry could stall a run for hours."

The message is required and is written as if the whole plan were one commit: what changed in the subject, why in the body. A bare subject is rejected. The plan moves to .clank/finished/. That is the seal.

With finish.autosquash on, the plan’s commits also collapse into one commit carrying that message. It rewrites the current branch in place, so it is off by default:

clank config finish.autosquash true

clank finish my-feature --no-squash -m "…" -m "…" keeps the individual commits for one finish, for example to keep a refactor bisectable. --force finishes without the gate’s say-so. That is the human’s escape hatch, not the master’s.

Setting a plan aside

  • clank stash takes the active plan’s commits off the branch and keeps them on a protective ref, so another plan can run. clank stash pop replays them, and they are reviewed afresh.
  • clank stash --to-queue gives the attempt up but saves the plan body back to the queue.
  • clank unfinish my-feature moves a finished plan back to active.
  • clank rereview makes every reviewer review the plan’s latest commit again. Use it when a commit was accepted without the review it needed.
  • clank purge --drop my-feature deletes a plan and its commits from history.

Blocks: questions only the human can answer

An agent that needs a decision it must not make itself asks for one:

clank block ask schema-choice -m "Keep the v1 config readable, or migrate it on first load?"

A block is repo-wide. While it is unanswered, the review cycle pauses for the whole team. Messages and events are still delivered. You answer it, naming the agent and the block, and the answer wakes the agent:

clank block answer alice schema-choice -m "Migrate on first load, and keep a backup."
clank block clean

Blocks are for real dependencies on you, such as contested reviews, a plan drifting from what you asked for, or work that looks unwise. A queued plan is an instruction, not a question, so the master never blocks to ask permission to do queued work. Set hooks.blocked to a command, such as a desktop notification, and clank runs it whenever an agent blocks.

Watching it happen

clank tui
clank log --plan my-feature --oneline

clank tui is the full-screen pane clank open puts beside the agents, and it is how you drive a running team. It shows each agent’s live state, the plan and its verdicts, the queue and drafts, event sources and the timeline, and it has a page for each agent with its auto-mode, tier and pane. Every screen lists its keys along the bottom.

clank log prints the same timeline: commits, reviews and GitHub events, newest first. clank status --watch re-prints the state as it changes, clank diff my-feature opens a plan’s diff in your editor, and clank html open renders the timeline as a static site.
